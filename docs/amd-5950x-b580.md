# 锐龙 9 5950X + Intel Arc B580 性能（`--corpus` harness，49 张）

口径与 [perf.md](./perf.md)（5800X + 3080 Ti）、[amd-h365-880m.md](./amd-h365-880m.md)（H 365 + 880M）、
[corpus.md](./corpus.md) 一致：`--corpus <backend>`，manifest NN 序，01_color 作 warmup 不计时，
其余 **49 张**逐张计 `Enhance` 端到端（解码在计时外）；pass1 含每尺寸的冷启动开销
（plan 编译、arena 增长），pass2 为同进程全量复跑（同时校验输出 hash 确定性）。

## 环境

| 项       | 值                                                                                         |
| -------- | ------------------------------------------------------------------------------------------ |
| CPU      | AMD Ryzen 9 5950X（Zen 3，16C/32T，两个 CCD 各 32 MB L3，AVX2+FMA，无 AVX-512）             |
| GPU      | Intel Arc B580（Xe2，20 Xe 核，12 GB GDDR6）；驱动 32.0.101.8331（Vulkan API 1.4.328）      |
| 内存     | 128 GB DDR4（双通道）                                                                       |
| OS       | Windows 11（10.0.26100），电源方案"高性能"                                                  |
| .NET     | SDK 10.0.401（运行时 10.0.12），`net10.0`，Release；glslc 来自 Vulkan SDK 1.4.357.0          |
| Commit   | 优化前 `5600cec`（main）；优化后 `8987b8a`（`perf/5950x-b580`）                               |

测速期间机器没有跑其他负载，测试、构建与测速不并行；优化前（`git worktree` 单独编一份 bench）
与优化后两个进程**交替**跑（base R1、new R1、base R2…），本机 run-to-run 抖动约 ±5%，
不交替的 A/B 不可信。

## 命令

```powershell
dotnet build bench/Sdcb.SimdGcdrNet.Benchmark -c Release
$exe = 'bench/Sdcb.SimdGcdrNet.Benchmark/bin/Release/net10.0/Sdcb.SimdGcdrNet.Benchmark.exe'

& $exe --corpus vulkan                                    # Vulkan
& $exe --corpus cpu                                       # CPU AVX2+FMA（本机默认档）
$env:DOTNET_EnableAVX2 = '0';        & $exe --corpus cpu  # CPU Vector<float>（128 位）
$env:DOTNET_EnableHWIntrinsic = '0'; & $exe --corpus cpu  # CPU Scalar

& $exe --bench 2304 1600 5      # CPU 单尺寸稳态，只计 gc+dr 推理（GCDRNET_PROF=1 GCDRNET_PROF_NODES=1 逐算子）
& $exe --benchcpu 2304 1600 5   # CPU 单尺寸稳态，真实 Enhance 路径（含前后处理，对齐 --benchvk 口径；本轮新增）
& $exe --benchvk 2304 1600 20   # Vulkan 单尺寸稳态（--vkprof 2304 1600 逐 shader，VKPROF_NODES=1 逐节点）
```

## 改了什么

### CPU：先测清楚

线程扩展（main，`--bench`，`GCDRNET_THREADS`）：

| 线程 | 8 | 16 | 24 | 32（默认） |
| ---- | - | -- | -- | ---------- |
| gc+dr | 778 ms | 605 ms | 577 ms | 575–605 ms |

8 → 32 线程只有 1.35×。绑核（`start /affinity`，`--benchcpu` e2e，`a11a70b` 之前测的）：

| 配置 | e2e |
| ---- | --- |
| CCD0 8 核，1 线程/核（0x5555） | 731 ms |
| CCD0 8C/16T（0xFFFF） | 738 ms |
| 两个 CCD 16 核，1 线程/核（0x55555555，16 线程） | 497–544 ms |
| 16C/32T 全部（默认） | 575–600 ms |
| 16 线程不绑核 | 705–713 ms |

逐节点 profile（自建的 scratch profiler，每个节点单独重复跑、取中位数，按算子类别求和；
单独跑一个节点时没有前后节点抢缓存/带宽，绝对值和 `--bench` 对不上，只看比例）：

| 类别 | 8 线程 | 16 线程 | 32 线程 | 8 → 32 |
| ---- | ------ | ------- | ------- | ------ |
| Conv Winograd + pool 融合 | 258.7 | 168.3 | 121.8 | 2.12× |
| UpHead | 193.4 | 101.7 | 60.9 | 3.18× |
| Conv stride 2 | 183.2 | 100.8 | 63.6 | 2.88× |
| Conv Winograd | 169.3 | 105.9 | 101.4 | **1.67×** |
| Conv + pool 融合（stem） | 164.3 | 87.5 | 55.6 | 2.96× |
| Gemm | 158.1 | 83.9 | 51.1 | 3.09× |
| ResizeBilinear | 22.8 | 24.2 | 25.4 | **0.90×** |
| ChannelShift / Elementwise | 17.9 | 18.3 | 17.1 | **不扩展** |
| LayerNorm | 7.4 | 36.7 | 28.6 | **0.26×** |

（ms。）

据此找到的不扩展的部分：

- **三个胶水核**（BGR u8 → float pad、div6 concat、crop → BGR u8）是**单线程**的，不在上表里，
  32 线程下一帧 ~93 ms（e2e 的 15%）。
- **Winograd GEMM**：16 → 32 线程几乎不涨，8 线程下也比预期慢。单独插桩三相（变换 / GEMM / 逆变换）
  后 GEMM 占绝大部分；看 JIT 反汇编，`TileAvx` 把 12 个累加器按值传给收尾的 `Store16`，在 x64 ABI 下
  这等于传引用，RyuJIT 于是把 12 个累加器全放在**栈上**，k 循环里每次 FMA 都变成 load + FMA + store，
  只跑到 FMA 峰值的 ~26%，SMT 兄弟线程之间还抢同一组 load/store 端口。
- **访存类**（bilinear、shift、逐元素）8 线程就已经顶到双通道 DDR4 的带宽，再加线程不变快；
  LayerNorm 更是 8 线程最快、16/32 线程慢 4–5 倍（节点很小，原因没有深挖）。它们合计只占 ~10%，
  本轮没有动。
- SMT 的收益是**负的**：同样 16 个工作线程，一核一个比挤在 8 核上（或交给调度器随意放）快得多；
  32 线程比 16 核×1 线程慢 ~10%。Zen 3 两个 SMT 线程共享一个核的 FMA 端口和 L1/L2，这个负载
  已经是 FMA/带宽受限，SMT 只增加争用。

### CPU：做了的

- **胶水并行化**（`5029371`）：`PixelOps` 的三个 NHWC 胶水核按行带切给 `Nhwc.For`，每个输出元素的
  计算不变（hash 逐张一致）。93 → 10 ms；e2e 632 → 579 ms。同时给 bench 加了 `--benchcpu`：
  原来的 `--bench` 只计 gc+dr 推理，看不到胶水。
- **AVX2 6×16 累加器留在寄存器**（`a11a70b`）：k 循环搬进不调用任何函数的 `TileAvxK`，结束时把
  12 个累加器写到 scratch tile（AVX-512 内核本来就是这样）；`TileAvx` 再对 scratch 行跑 `Store16`
  收尾（residual / 激活 / 写回）。12 个累加器 + 1 个广播 + 2 个权重 = 15 个 ymm，JIT 反汇编确认
  循环里没有栈访问。Winograd 的 36 个小 GEMM 直接从 `TileAvxK` 写 M 行。每个输出元素的 FMA 序列不变，
  输出逐位相同。gc 的 32 → 128 Winograd conv+pool 单线程 144 → 69 ms、32 线程 37 → 14 ms；
  `--bench` 579 → 373 ms（gc ~139 / dr ~234 ms）。Vector 档不受影响（它走 `TileVec`），AVX-512 档没动。

### CPU：试过没收益、放弃的

- **Winograd 块大小**（vBudget 65536 / 32768 / 16384 / 8192 floats × 16/32 线程，按 32 MB/CCD 重扫）：
  所有组合都在 ±5% 噪声内，交替重复后没有稳定的赢家，保持原值（880M 那轮按 Zen 5 扫出的值）。
- **改默认线程数**：16 线程、1 线程/核（0x55555555）比默认 32 线程快 ~10%（最终 HEAD 上
  `--benchcpu` 342–350 vs 387–390 ms），但这个收益**完全来自进程亲和**：同样 16 线程不绑核反而更慢
  （418–441 ms），因为调度器会把两个工作线程放到同一核的两个 SMT 上。库没有办法在不动进程/线程
  亲和的前提下拿到这 10%，而改亲和是侵入性的（宿主进程里还有别的线程），也不跨平台；
  只改线程数会变慢。所以默认保持 `Environment.ProcessorCount`。需要压延迟的部署可以在启动时
  绑一核一线程（`start /affinity 55555555`，`GCDRNET_THREADS=16`）。
- **按 CCD 绑核**（同一张图的线程留在一个 CCD）：单 CCD 8 核 731 ms，远慢于两 CCD；
  跨 CCD 的 L3 不共享并不是瓶颈，算力才是。没有做。
- **更大的微内核**：Zen 3 只有 16 个 ymm，6×16 已用满（见上），没有尝试。

### Vulkan：做了的

- **XMX 卷积：sg16 + 8×16×16**（`16568f8`）：`conv_cm.comp` 新增 SG16 变体（只与 LITE 组合：
  B580 只有 32 KB 共享内存）。A 片/累加器 8 行、16 lane subgroup，staging、k 顺序、收尾与 LITE 相同；
  BM 仍是 128，派发不变。tile 形状在 B580 上扫过：每个 subgroup 一条 16×32、M 向叠 8 个 subgroup
  （BN 128 / 64 / 32 = 512 / 256 / 128 线程）最快；32×32 条带慢 10–25%，64×32 / 32×64 寄存器溢出（2× 慢）。
  门控（`VkDevice.CoopM8`）：16×16×16 + 32 lane 优先（NVIDIA、880M 不变）；只有没有它、有 8×16×16、
  16 在 compute 可 pin 范围内时才选 SG16，管线带 `requiredSubgroupSize = 16` + `REQUIRE_FULL_SUBGROUPS`，
  建设备时 `sgprobe` 必须报 16 lane，否则退回 `conv_tile`。`GCDRNET_VK_SG16=0` 关闭。
  84.4 → 35.4 ms。
- **4 通道访存 shader 在 Intel 上也开**（`4874fdc`）：maxpool / bilinear / depthwise / shift 的 `*4`
  变体原来只在核显上开。B580 上每元素四次整数除法在 SIMD16 上很贵，四个算子合计 10.4 → 6.7 ms，
  `--benchvk` 38.8 → 35.5 ms。门控：核显 || vendor 0x8086；NVIDIA / AMD 独显不变。
- **3×3 stem conv+pool 每个输入只读一次**（`8987b8a`）：sg16 之后 dr 的 stem（6 → 32 通道、全分辨率
  conv + 2×2 pool，`convpool`）是最大单项 6.3 ms。原 shader 对 2×2 池化窗口里的 4 个 conv 输出
  逐个算，每个输入元素读 2.25 次、每对权重从共享内存读 4 次。`convpool_k3.comp`（仅 3×3）把
  4×4 输入窗口一行行读进寄存器，每对权重同时喂两列池化输出；线程映射和每个输出的累加顺序
  与 `convpool` 相同，**输出逐位相同**（关掉它跑语料，49/49 hash 一致）。dr stem 6.26 → 3.76 ms，
  gc stem 1.26 → 1.13 ms；`--benchvk` 35.6 → 33.0 ms，语料 39.0 → 36.4 ms/张。
  门控 Intel（`VkDevice.ConvPoolK3`），`GCDRNET_VK_CONVPOOL3=0` 关闭。

### Vulkan：已有的 / 确认过的

- **队列**：`VkDevice` 本来就优先选不带 GRAPHICS 位的 compute-only 队列族；B580 上是 qf1
  （flags 0x2，4 个队列，对应独立的 CCS 引擎），不需要改。
- **`convpool` / `uphead_sc`**（main 内存一轮的融合 shader）在 B580 上正确（golden / 语料），
  耗时占比见下表；`uphead_sc` 是现在的第三大项。

### Vulkan：试过没收益、放弃的

- **convpool 一线程一像素 × 全部输出通道**（每个 subgroup 广播同一份权重）：dr stem 6.25 → 5.54 ms，
  但 gc stem（16 通道）1.27 → 2.07 ms（并行度只剩 1/2–1/4），合计持平，放弃。
- **convpool 权重循环放最外、每 tap 4 次标量读**：dr 4.19 ms，比最终版（3.76 ms）慢，被取代。
- **sg16 的其他 tile 形状**：见上（32×32 条带、64×32 / 32×64 条带）。
- `conv_tile` 的 Arc 调参：XMX 路径打通后它在 B580 上只剩 `GCDRNET_VK_COOPMAT=0` 的退路，没有再调。

## 正确性

- ISA 矩阵（当时的 `test-all.ps1`，现由 CI 跑）：AVX2（默认档，本机无 AVX-512）、AVX2（`DOTNET_EnableAVX512=0`、`DOTNET_EnableAVX512F=0` 各一次）、Vector、SSE、Scalar 六档全部通过（129 个测试；每档跳过 34 个 AVX-512 对比测试，Scalar 另跳过 4 个 Winograd 测试），Vulkan 测试（52 个）在每一档里都跑。
- Vulkan 测试另外在 `GCDRNET_VK_F16=0`、`GCDRNET_VK_COOPMAT=0`、`GCDRNET_VK_SG16=0`、
  `GCDRNET_VK_VEC4=0`、`GCDRNET_VK_CONVPOOL3=0` 下各跑一遍（`VulkanTests` + `VkKernelTests` + `VkDebugTests`）：六种配置（默认 + 五个开关）全部通过（52 个；`COOPMAT=0` / `SG16=0` 下 15 个 coopmat kernel 用例按设计跳过，整网走 `conv_tile`；`F16=0` 下走 fp32 存储的 `convpool_k3.spv`）。
- 新内核的单元测试：`VkKernelTests.ConvCm_MatchesCpu` 新增 5 个针对 SG16 的形状（oc 16 半个 N tile、
  不满的 N tile + residual + gelu、cin 8 stride 2 反射填充、任意 cin 的 stem（cin 3/6）+ 收尾、深 K），
  原有的 10 个 case 也都跑在 SG16 上；`CoopGate_Consistent` 检查门控互斥；
  `ConvPool_MatchesCpu`（`convpool` / `convpool_k3` 对 CPU `Nhwc.ConvPool`：反射/常数/非零 pad 值、
  conv relu / pool relu、cin 1 / 3 / 6 / 7、不满的最后一个 workgroup）。
- **反向验证**：把 SG16 管线的 `requiredSubgroupSize` 改成 0（驱动默认 32 lane），15 个 coopmat kernel
  用例和 12 个 Vulkan golden 测试全部失败（pin 成 32 也一样），说明测试能抓到 lane 映射错误。
- NVIDIA / 880M 路径：用当前 glslc 重编全部 shader，**既有 .spv 逐字节一致**（只多出
  `conv_cm_sg16*_h.spv` 与 `convpool_k3*.spv`）。SG16 门控要求 16 在 subgroup 可 pin 范围内且
  没有 16×16×16：3080 Ti（固定 32）、880M（32–64）都触发不了；`Vec4Eltwise` / `ConvPoolK3` 的扩展
  只针对 vendor 0x8086。**3080 Ti / 880M 未实测**。
- 语料：所有档位、所有轮次 pass1/pass2 输出 hash 一致；CPU 三档与 main 49/49 逐张一致，
  PSNR 24.65 dB（24.6492），Vulkan 24.68 dB（24.6757）。

同为内存优化后的 main 口径；5800X + 3080 Ti 取自 [perf.md](./perf.md)，H 365 + 880M 取自

| Vulkan 单尺寸稳态 | ~17 ms | 88.5 ms | **32.9–33.0 ms** |
| Vulkan 显存 / peak WS | 420 / 332 MB | 420 / 730 MB | 420 / 276 MB |

## 观察

- **B580 的频率态会漂**：同一构建的 `--benchvk` 在不同时段有 35.4 / 38.8 / 40.4 ms 几档，
  跑一阵后会稳定在某一档，所以每个 A/B 都要交替跑。语料上没有出现 3080 Ti 那种"两张图之间
  GPU 空闲 → 降频 → 单张变慢"的明显现象：Vulkan pass2 比 pass1 快 2–3%（只差 plan 编译），
  三轮 pass1 波动 ±0.5%，语料均值 36.4 ms/张与单尺寸稳态按像素数折算基本一致。
- **XMX 打通之前 B580 比 5950X 的 CPU 只快 7×**：base 语料 Vulkan 89.2 vs AVX2 653.1 ms/张，
  `conv_tile` 是 SIMD16 上的普通 fp32 FMA。8×16×16 + sg16 之后卷积不再是瓶颈：
  GPU 时间里 coopmat 卷积约 40%（gc 6.9 / dr 9.4 ms，合计 40.8 ms），剩下的是 stem / UpHead 的融合 shader、layernorm 与访存类。
- **5950X 的 SMT 是负收益**（见上）；双通道 DDR4 对 16 核也偏紧：bilinear / shift / 逐元素
  8 线程以上不再变快。
- **Vector 档几乎没变**（991.5 → 953.3 ms/张，只有胶水并行的收益）：`TileVec` 走 128 位
  `Vector<float>`，寄存器压力不同，没有改它。AVX2 → Vector 的差距因此从 5800X 的 1.33× 拉到 2.30×。
- **后续可做**：`uphead_sc`（dr 3.9 ms）也可以按 `convpool_k3` 的思路把 skip 重算的 3×3 窗口按行读入；
  layernorm（gc+dr 4.4 ms）在 SIMD16 上用 subgroup 归约；CPU 侧 `TileVec` 的同类寄存器检查、
  LayerNorm 在多线程下变慢的原因。
