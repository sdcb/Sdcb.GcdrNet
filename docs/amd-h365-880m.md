# 锐龙 AI 9 H 365 + Radeon 880M 性能（`--corpus` harness，49 张）

口径与 [perf.md](./perf.md)（5800X + 3080 Ti）、[corpus.md](./corpus.md) 一致：`--corpus <backend>`，
manifest NN 序，01_color 作 warmup 不计时，其余 **49 张**逐张计 `Enhance` 端到端（解码在计时外）；
pass1 含每尺寸的冷启动开销（plan 编译、arena 增长），pass2 为同进程全量复跑（同时校验输出 hash 确定性）。

## 环境

| 项       | 值                                                                                   |
| -------- | ------------------------------------------------------------------------------------ |
| CPU      | AMD Ryzen AI 9 H 365（Zen 5，4× Zen 5 + 6× Zen 5c，10C/20T，AVX-512，256 位 FP 数据通路） |
| GPU      | AMD Radeon 880M（RDNA 3.5 核显，12 CU）；驱动 32.0.31041.1004（Vulkan：AMD proprietary 26.8.1 / LLPC，API 1.4.349） |
| 内存     | 32 GB LPDDR5X-7500（与 GPU 共享；Vulkan 报 11 GB DEVICE_LOCAL heap + 5.4 GB 系统 heap） |
| OS       | Windows 11 专业工作站版 26200                                                        |
| .NET     | SDK 10.0.401，`net10.0`，Release                                                      |
| 电源     | 插电（充电中），Windows 电源模式"最佳性能"（方案"平衡" + 最佳性能叠加）                 |
| Commit   | 优化前 `73f0e2f`（main，含内存优化一轮）；优化后 `5dd36e1`（`perf/avx512-880m`）       |

测速期间机器没有跑其他负载，测试、构建与测速不并行；优化前后两个构建在同一时段先后跑。

## 命令

```powershell
dotnet build bench/Sdcb.GcdrNet.Benchmark -c Release
$exe = 'bench/Sdcb.GcdrNet.Benchmark/bin/Release/net10.0/Sdcb.GcdrNet.Benchmark.exe'

& $exe --corpus vulkan                                    # Vulkan
& $exe --corpus cpu                                       # CPU AVX-512（默认，支持时）
$env:DOTNET_EnableAVX512 = '0';      & $exe --corpus cpu  # CPU AVX2+FMA
$env:DOTNET_EnableAVX2 = '0';        & $exe --corpus cpu  # CPU Vector<float>（128 位）
$env:DOTNET_EnableHWIntrinsic = '0'; & $exe --corpus cpu  # CPU Scalar

& $exe --bench 2304 1600 5      # CPU 单尺寸稳态（GCDRNET_PROF=1 GCDRNET_PROF_NODES=1 打开逐算子 profile）
& $exe --benchvk 2304 1600 20   # Vulkan 单尺寸稳态（--vkprof 2304 1600 逐 shader）
```

ISA 档位通过 JIT 开关强制降级，与 `test-all.ps1` 的矩阵一致。.NET 10 的 JIT 只认
`DOTNET_EnableAVX512=0`（`DOTNET_EnableAVX512F=0` 被忽略、`Avx512F.IsSupported` 仍为 true），
所以库自己也读 `DOTNET_EnableAVX512F=0`（以及 `GCDRNET_AVX512=0`）来关掉 AVX-512 档，
两个开关都会退回 AVX2，`test-all.ps1` 两个都跑。

## 改了什么

### CPU：AVX-512 档

档位顺序 AVX-512 → AVX2 → Vector → Scalar，按 `Avx512F.IsSupported` 分发。所有 AVX-512 内核
对每个输出元素保持 AVX2 的运算顺序（bias 初值、tap → 通道升序、逐个 FMA）和收尾运算，
**输出与 AVX2 档逐位相同**；`Avx512KernelTests` 在同一进程里切换两档逐位比对。

- **卷积 / Gemm 微内核**（`Nhwc.Avx512.cs`）：10 像素 × 32 oc（两个打包的 16-oc 块，各一个 zmm，
  20 个累加器），奇数块数用 10 × 16 的尾内核。6 / 8 / 10 / 12 / 14 行实测差 3% 以内，10 行最好。
  k 循环只写 scratch tile，residual / 激活放在循环外（循环里有调用会让 RyuJIT 把累加器放到栈上）。
  tile 的列不需要填充时，把一行卷积核的 kw 个 tap 当成一段 kw×ic 的连续输入（与打包权重的
  [tap][ic] 顺序一致），3/6 通道的首层指针少、k 循环长。
- **融合路径**：main 的内存优化把一部分直接卷积改成逐行调用（conv+maxpool 的条带、UpHead 的
  skip 重算），这里加了行级入口 `Dense512Row`，`ConvPool` 与 UpHead（两档）都经 `ConvRow` 按档位分发；
  Winograd 的 AVX-512 部分并进了 `WinoArgs` / `WinoTiles`，融合的 Winograd 条带同样走 10×32。
- **Winograd**：36 个小 GEMM 走 10 × 32 内核，M 改成 [36][T][32] 让内核直接写入；输入/输出变换用
  16 lane 向量；变换块从 ~256 KB 缩到 ~64 KB（16K–256K floats 实测最好，1 MB 慢 27%）。
- **访存类算子**：maxpool 在寄存器里取完所有 tap 再写一次；bilinear / UpHead 的插值用 16 lane；
  UpHead 的 c 长点积原来是每像素一条串行 FMA 链（受 FMA 延迟限制），改成 4 个像素交错。
  这些算子基本是带宽瓶颈（本机实测读 ~75 GB/s），收益只在隔离测试里明显
  （UpHead c=32 14.1 → 12.4 ms、maxpool 13.9 → 11.9 ms），端到端在噪声内。

**Zen 5 移动版上 AVX-512 值不值？** 值。这颗 CPU 的 FP 数据通路是 256 位（zmm 指令拆两半执行），
理论 FLOPS 与 AVX2 相同，但：zmm 有 32 个寄存器，10 × 32 的 tile 每次广播喂两条 FMA、每个 k 步
只发一半的 load/broadcast，前端和 load 端口压力明显下降；Winograd 变换的指令数也减半。
卷积相关整体约 1.9×；访存类算子与 AVX2 基本持平（因此没有单独去改 LayerNorm、shift、
逐元素等，它们仍走 AVX2 实现）。

### Vulkan：880M

`GCDRNET_VK_VERBOSE=1`：

```
[vk] device=AMD Radeon(TM) 880M Graphics type=1 vendor=0x1002 qfamily=1 sg=64 sgRange=32-64 sgcCompute=True
     push=True coopmat=True coopSg=32 fullSg=True lite=True vec4=True lds=32768 sb16=True
[vk] heap0: 5511 MB flags=0
[vk] heap1: 11022 MB flags=3
```

- **coopmat**：16×16×16 f16→f32 subgroup 配置是有的，但默认 wave64，原来的门控
  （subgroup 必须 32）直接把张量核心卷积关了，所有卷积和 Gemm 走 `conv_tile`。
  现在探测 `VK_EXT_subgroup_size_control`：默认宽度不是 32、但 32 在 compute 的可选范围内时，
  启用扩展（含 computeFullSubgroups），coopmat 管线带 `requiredSubgroupSize = 32` +
  `REQUIRE_FULL_SUBGROUPS` 创建；建设备时跑一次探针 shader（256 线程），必须每个 invocation
  都报 32 lane、8 个 subgroup，否则 coopmat 保持关闭、退回 `conv_tile`，**不会出现 lane 映射错位
  而静默算错**（把 required size 临时去掉，22 个 coopmat / Vulkan 测试全部失败，说明测试能抓到）。
- **共享内存 32 KB**：原来双缓冲的 BN=128 tile 要 48 KB（n64 34 KB）。新增 LITE 变体（参考
  SimdPaddleOCR 的 sg32l）：单缓冲 staging；收尾的 stage 与 staging 共用同一块 `uvec4` 共享内存
  （coopmat load/store 允许元素类型与矩阵类型不同）；标量收尾；按 4 个 N 列分组光栅化。
  BN 128 / 64 / 32 的 tile 只占 10–20 KB。
- **tile 形状**：在 880M 上扫了十来种配置，"每个 subgroup 一条 64×16 的窄条、每个 tile 多放
  subgroup"（BN 128 / 64 / 32 分别 512 / 256 / 128 线程）最快：dr 的 BN=128 卷积合计 27.3 → 12.5 ms
  （原配置是 8 个 subgroup 各 64×32）。BM=256（端到端 88 → 166 ms）和每 subgroup 16 个累加块
  （BN=128 卷积 1.8× 慢）都输在寄存器压力上。首层的 k → (tap, ci) 除法提到行循环外。
- **访存类 shader**：maxpool / bilinear / depthwise / shift 原来每个 invocation 一个元素、四次整数除法、
  2 字节标量读；核显上改为每 invocation 4 通道（`*4.comp`，c % 4 == 0），只在集成 GPU 上启用。
- **main 的融合 shader**：stem 的 conv+pool（`convpool`）与 UpHead skip 重算（`uphead_sc`）不走 coopmat：
  带 `Pool` 的卷积被 `UseCoopConv` 排除，不会进 LITE；Vulkan 计划里只剩两个非 stem 的 maxpool
  （走 `maxpool4`）。这两个 shader 现在是 880M 上最大的单项（dr：11.0 / 12.7 ms）；
  `GCDRNET_NOFUSE_MEM=1` A/B 端到端 85.9 vs 87.2 ms，融合在核显上慢 ~1–2%，换来更小的 arena（main 那一轮内存优化合计显存 1289 → 420 MB），保留。
- **统一内存**：staging 本来就是零拷贝——BGR 输入落在 DEVICE_LOCAL | HOST_VISIBLE | HOST_COHERENT
  （type2，heap1），回读落在 HOST_CACHED 系统内存（type3），都常驻映射，帧内没有 copy 命令；
  剩下的只是 CPU 侧两次 ~11 MB 的 memcpy，没有可省的 GPU 拷贝。arena 预算：集成 GPU 上
  "设备本地"其实是与 CPU 共享的系统内存，worker arena（main 之后 gc+dr 共用一块）与空闲 worker 的
  预算改为 min(3 GB, heap/4)（本机 11 GB heap → 2.7 GB；本语料单 worker 只用 420 MB，结果不受影响）。
- **NVIDIA 路径不变**：3080 Ti 默认就是 32 lane，不启用新扩展、不 pin subgroup、不走 LITE
  （共享内存 ≥ 48 KB）、不用 `*4` shader，原有 `conv_cm*.spv` 重新编译逐字节一致；
  预算只在集成 GPU 上收紧。新逻辑全部按设备能力门控（subgroup 范围、共享内存、设备类型），
  可用 `GCDRNET_VK_SG32=0`、`GCDRNET_VK_LITE=0`、`GCDRNET_VK_VEC4=0`、`GCDRNET_VK_COOPMAT=0` 关闭。

单尺寸 GPU 时间（`--vkprof`，gc + dr ≈ 105 ms，含逐 dispatch 时间戳开销）：

| shader | gc | dr |
| ------ | -- | -- |
| conv_cm（BN 128/64/32） | 14.5 ms | 24.4 ms |
| convpool（stem conv + 2×2 pool） | 3.4 ms | 11.0 ms |
| uphead_sc（tail + skip 重算） | 4.9 ms | 12.7 ms |
| maxpool4 | 3.1 ms | 3.8 ms |
| layernorm | 3.5 ms | 4.0 ms |

## 正确性

- `./test-all.ps1`：AVX-512（默认）、AVX2（`DOTNET_EnableAVX512=0`、`DOTNET_EnableAVX512F=0` 各一次）、
  Vector、SSE、Scalar 六档全部通过（118 个测试；非 AVX-512 档跳过 34 个 AVX-512 对比测试，
  Scalar 另跳过 4 个 Winograd 测试），Vulkan 测试在每一档里都跑（41 个，含 coopmat LITE、
  4 通道 shader 的 kernel 测试）。
- 新内核的单元测试：`Avx512KernelTests`（直接卷积 / Winograd / Gemm / maxpool / resize / UpHead /
  conv+pool 融合 / UpHead skip 重算，与 AVX2 逐位比对；整网内存融合在 AVX-512 下与不融合的 AVX2
  逐位一致）；`VkKernelTests`（LITE coopmat 带 residual、gelu、不满一组的光栅化；
  maxpool4 / bilinear4 / shift4 / depthwise4 对 CPU 内核）。
- 语料：所有档位、所有轮次 pass1/pass2 输出 hash 一致；CPU 各档 PSNR 24.65 dB，Vulkan 24.68 dB。

## 观察

- **核显在 main 上跑 Vulkan 比 CPU 还慢**：优化前 Vulkan 392.1 ms/张，AVX2 534.4 ms/张，只快 27%。
  原因就是 wave64 把张量核心门控掉了，`conv_tile` 占 GPU 时间 ~80%（`1af112a` 上 `--vkprof` 合计 ~350 ms）。
  subgroup 固定到 32 后 coopmat 卷积合计 ~39 ms，现在 Vulkan 语料比 AVX-512 快 2.9×。
- **880M 喜欢"更多、更窄"的 subgroup**：同样 BN=128，8 个 subgroup 各 64×32 比 16 个各 64×16
  慢一倍。推测是 WMMA 吞吐够用、瓶颈在共享内存/全局读的延迟，更多 wave 才盖得住。
- **剩下的 GPU 时间**：coopmat 卷积 ~39 ms，stem 的 convpool + uphead_sc ~32 ms（逐元素 gather、
  每像素重算 skip 卷积，都不走张量核心），其余访存类 ~25 ms。下一步最值得做的是这两个 stem shader。
- **语料的 pass1/pass2**：Vulkan pass2 比 pass1 快 2%（plan 编译只在 pass1），没有出现 3080 Ti 上
  调频把 pass2 拖慢的现象；CPU 各档 pass2 与 pass1 相差 0.1–3%。
- **CPU 档位差距**：AVX2 → Vector 1.38×（5800X 1.33×），Vector → Scalar 8.5×（Winograd 需要 SIMD，
  Scalar 只吃到融合与紧凑 arena 的收益）。
- **后续可做**：stem 的 convpool / uphead_sc 在核显上改成 LDS 暂存 patch 的版本；PoolBand 的 16 lane 版；
  CPU 的 16-oc 首层（gc）用 20 行 × 16 的内核。
